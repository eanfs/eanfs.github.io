资料核验：2026 年 11 月 21 日约 17:50—18:20（上海时间），依据 Karpo 官方发布博文、machinepulse-ai/karpo-browser 与 machinepulse-ai/karpo-decision 当时的 GitHub 元数据、Apache-2.0 许可证和 README，以及 Karpo Decision 27B Act 模型卡 和 Karpo BrowserBench 页面。仓库、模型卡和评测数字都会变化，细节请以各官方页面最新文本为准。文中的准确率、耗时和费用均来自官方自述或官方写明的评测说明，作者没有安装、运行或复现这些工具与评测，也不构成选型或安全背书。

“让智能体自己打开网页把事办完”，是现在很好卖的一句话。读到发布稿里的准确率和每项任务费用，人很容易把三件事当成一件事：谁在做计划，谁在页面上点选，以及这个数字到底是在什么口径下测出来的。

这和本博客谈开源项目要分清“宣称支持”和“默认可用”是同一类问题，只是对象从平台清单换成了浏览器智能体的任务拆分和评测口径。它也和给编程智能体放权之前，先想清楚它在哪里必须停下有关，但本文不展开权限清单，只看官方文档把规划和点击分开之后，成绩与边界应该怎么读。

一、先分清谁在规划，谁在点击

2026 年 11 月 21 日，Karpo 发布了开源项目 karpo-browser，并同时放出页面操作模型 Karpo Decision 27B Act。当天约 17:50 用 GitHub 接口读取的元数据是：karpo-browser 为公开仓库，许可证 Apache-2.0，语言 TypeScript，星标 0，fork 0；仓库创建于 2026 年 11 月 21 日 01:43（上海时间），最近一次推送在当天 05:09，当时能读到的提交说明是 karpo-browser 0.1.0。配套推理代码仓库 karpo-decision 同样是 Apache-2.0，当时星标 29。星标会继续变化，请以仓库页面当时的数字为准。

它要处理的，是浏览器智能体里最常见的一种做法：让同一个通用大模型决定每一个点击、输入和滚动。karpo-browser 把工作拆成两层。规划层被叫做 System 2，由 Claude Code、Codex 或开发者自己的智能体承担：把用户任务拆成目标，写出可以填进表单的值，阅读页面，比较选项，并在目标完成后作答。操作层被叫做 System 1，由决策模型承担：它看到的是截图、编号后的页面元素、当前目标和最近几步的变化，然后在给定选项里选一步。官方说明是一次前向计算、不生成长文本。

官方 README 把一次运行的结束状态写得很清楚。done 只表示 System 1 判断目标已经达到，还要由 System 2 对照页面再检查；needs_approval 表示下一步涉及付款、预订或难以撤回的操作；此外还有缺值、站点无法提供、被拦截、循环和超时等状态。MCP 接口也按这个分工来：run_browser_agent 把目标和可填写的值交给 System 1，read_page 把编号后的页面交回给规划模型，必要时还可以由规划模型手工点击或输入。

官方模型卡还给出了一组他们自己跑基准时的分工数字：在最终配置的 3 次全量任务运行中，System 1 承担了约 78% 的页面操作（不含打开网址），却只占用每项任务约 14% 的时间和约 13% 的模型费用。这些数字说明的是他们那次评测里两层模型分别干了多少活，不能单独证明换一套网站或换一个规划模型后，费用结构仍然相同。

二、发布稿里的准确率，要先问是不是排行榜成绩

官方博文和模型卡都把这样一个结果放在最前面：在 Browserbase Benchmark v2 的 38 个核心任务上，karpo-browser 用 DeepSeek V4.1 Flash 做 System 2、用 Karpo Decision 27B Act 做 System 1，8 次运行的平均任务准确率是 84%，平均智能体运行时间 218 秒，模型费用估计为每项任务 0.096 美元。

把这组数字当成“已经打上官方排行榜的成绩”，并不符合他们自己的说明。模型卡写得很直接：这些是他们自己的运行，不是榜上的记录；他们统计的是智能体自身的运行时间，而榜上每条记录是单次运行。评测程序用的是 Stagehand 在 2026 年 11 月 10 日的开源评估代码，外加接入 karpo-browser 的补丁，默认评判模型是 Gemini 3.5 Flash；他们写明，并未核实榜上记录是否使用同一版本的评判程序和评判模型。计时只包含智能体运行时间，不含评分，单项限额 450 秒；他们也写明，没有找到榜方关于计时边界的说明。

费用同样要拆开看。0.096 美元里，System 2 按当天 OpenRouter 公开价格乘以实际 token 计算，System 1 则是按“同等规模 Qwen 模型的公开输入价”每百万 token 0.06 美元来估的——因为 Karpo Decision 27B Act 没有公开 API。模型卡写明，按实际 GPU 时间计算，模型费用会落到每项任务 0.11 到 0.14 美元。Browserbase 云浏览器费用大约每项任务 0.33 到 0.38 美元，以及评分费用，都不包含在这个数字里。

还有一个容易被标题数字盖住的细节。官方材料里，102 项全部任务的汇总并不只给出一个数。博文写过三组运行的平均准确率 88.9%；模型卡把“最终配置、平均耗时最短的那一组三次运行”写成 86%，又写 8 次全量运行平均通过 88.8 项，最准的一组两次平均约 89%。38 个核心任务的 8 次结果，通过数从 29 到 35 不等，也就是大约 76% 到 92%。更稳妥的读法是：先看他们公布的是哪一组运行、是核心集还是全集，再看平均值背后的波动，而不是只记住最显眼的 84%。

模型卡还加了一句限制：评测中的 DeepSeek V4.1 Flash 是 10 月 17 日的版本并打开了图像输入，karpo-browser 的运行框架也在这套任务上做过调整，因此“不能把它看成与榜上其他 DeepSeek V4.1 Flash 记录的受控对比”。官方自己把这句话写出来，比任何外部评论都更值得先读。

三、任务做完了，不代表每一步决策都选对

在线基准回答的是：在真实网站上，这件任务有没有做完。可是任务失败时，人们还想知道是哪一步点错了。Karpo 为此做了 Karpo BrowserBench（KBB）：用录好的真实页面逐步回放，让不同模型面对同一组固定输入，逐步打分。官方页面写明，KBB 1.0 覆盖 787 条任务、23,075 步，来自 584 个网站；一条指令只有每一步都选对，才算完成，平均 7.6 步。

在线任务完成率，和逐步决策正确率，不是同一个指标。官方给出的 2026 年 11 月 17 日私有分割快照是：Karpo Decision 27B Act 的指令完成率是 35.5%，逐步准确率 78.5%；当时榜上四个通用大模型的指令完成率是 38.1% 到 41.0%。也就是说，在他们自己的逐步基准上，这个专为网页操作微调的模型，完成率并没有高于这几个通用模型。模型卡也承认：榜上其他决策模型往往只读页面文本，而它和通用大模型一样会看截图，对那些决策模型的领先，有一部分来自输入不同。

所以，把“更快、更便宜”直接读成“逐步决策也更准”，并不符合当前公开的 KBB 数字。更稳妥的用法是把两类评测分开：在线基准看任务能不能做完，逐步基准看在固定页面上会不会选错；再把费用、延迟和完成率放到一起看，而不是只比较最容易传播的那个百分数。

四、文档里的边界，也不宜直接当成已经拦住的闸门

规划和使用操作模型分开之后，付款、登录和密钥仍然要单独看。

官方 README 把 needs_approval 解释为：下一步涉及付款、预订或难以撤回的操作，规划层只有在任务允许时才继续。博文写得更具体：对付款或预订这类动作，审批边界取决于 System 1 在目标权限不足时选择 NEEDS_APPROVAL。换句话说，这是模型按目标描述做出的状态判断，而不是文档里已经写死、与模型无关的硬拦截。如果规划层使用 Codex，README 还提到：Codex 会在每个会操作页面的工具调用前询问。这是另一层来自客户端的确认，和 System 1 自己报出的状态不是一回事。

密钥的说法也要对照着读。README 写：用 --secret 或 run() 里的 secrets 提供的值，会按名字被输入到页面上，不发送给任何模型，随后在 System 1 读到的内容里也会被遮罩。官方博文则补充：运行框架会把密钥的名字作为文本传给模型；向页面填入密钥后，不再把截图发给 System 1，但 System 2 在启用图像输入时仍可能收到截图。更稳妥的理解是：官方保证的是密钥的值不进入模型，不是“名字和填入后的页面图像对所有模型都不可见”。

安装路径也值得先核验。README 给出了 npm install -g karpo-browser，并挂了 npm 徽章。2026 年 11 月 21 日核验时，npm 官方注册表 和 unpkg 对该包名的访问都返回 404；仓库里的 package.json 版本是 0.1.0。这不一定意味着项目不可用，只说明在发布当天，文档里的全局安装命令还不能被当成已经上架的安装路径。要从源码使用，应回到仓库说明，而不是默认 npm 徽章已经指向一个可下载的包。

写在后面

浏览器智能体要不要用，先不必被一次发布稿里的准确率带着走。更值得先问清楚的，是这三层：任务是如何拆给规划模型和页面操作模型的；公开成绩是在线任务完成率还是逐步决策正确率，以及它是不是排行榜上的正式记录；付款、登录和密钥在文档里是靠模型申报状态、客户端确认，还是与模型无关的硬限制。把这三层分开，数字才比较好读。
