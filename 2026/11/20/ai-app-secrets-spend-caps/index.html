用 AI 搭出来的应用要上线，先查数据存在哪、谁能访问，再堵密钥和费用

资料核验：2026-11-20（上海时间），依据 Supabase、Firebase、Amazon S3、OWASP、MDN，以及 Vite、Next.js、OpenAI、Stripe 和 Resend 的官方文档。各产品文档会更新，配置入口和限制请以官方最新页面为准。本文只转述这些页面公开写明的数据访问方式、密钥类型和费用控制。作者没有检查某个具体应用的数据库、存储桶或构建产物，也没有复现或测试任何泄露，不构成安全审计或上线验收。

用编程助手很快就能搭出一个“能跑”的应用：预约、聊天助手、收款、发邮件，浏览器里一点，接口就通了。上线前第一个该问的，不是仓库里有没有明文密钥，而是用户数据实际存在哪里，以及谁能读写。

预约记录、聊天记录、个人信息和上传的文件，可能在你自己的数据库里，也可能在 Supabase、Firebase 这类 BaaS、对象存储、第三方服务及其日志，或浏览器的本地存储里。位置没列出来，后面的访问控制就无从核对。密钥和费用是接下来的两层：有些环境变量会按设计被写进用户下载的前端包。密钥一旦进了这个包，gitignore 拦不住，删除源码里的那一行也来不及——访客的浏览器里可能已经有一份拷贝。更麻烦的是，如果这条密钥对应的账单只有提醒、没有硬上限，损失窗口会比你想象的更长。

这和本博客谈编程智能体必须在哪些动作上停下不是同一层问题。那一篇问的是智能体在仓库和发布流程里能做什么；这一篇问的是它交出来的应用，上线后用户数据、密钥和费用会不会被不该拿到的人碰到。

一、先问数据在哪，再问谁能读写

编程助手为了让预约、聊天或文件上传先跑起来，常常会直接接上 Supabase、Firebase，或一个对象存储桶。这些服务里，有的客户端标识按设计就可以出现在浏览器中。用户数据能不能被读写，取决于访问控制有没有打开、策略怎么写，而不是这条标识藏没藏好。

Supabase 的 API keys 把密钥分成两档。发给浏览器、移动应用或写进源码的，用 publishable key（sb_publishable_...）。选择表写明：你发出去的代码谁都能读到它，所以它只能访问 Row Level Security 允许的数据；密钥类型表里，它的用途是 “Safe to expose online”。secret key（sb_secret_...）只用于你自己控制的后端。它绕过 Row Level Security，并能完整访问项目数据。anon 和 service_role 分别是这两档的旧版。文档写明二者将在 2026 年底弃用；在控制台停用之前，它们仍然有效。

Securing your data 补上了前提：publishable key 在开启 RLS 之后才适合暴露，因为每一行能否访问，要对照访问策略和用户的 JWT。旧项目里的 anon key 按同样方式对待：它可以标识项目，但不是机密，必须配上 RLS，以及只授予必要权限的 grant。secret key 和 service role key 会绕过 RLS。官方写明它们永远不适合暴露，只能放在后端。

没开 RLS 时，Tables and data 写得很具体：public schema 里的表可以通过 Data API 访问；在启用行级安全并写好策略之前，任何持有该项目 publishable key 的人都能读写其中的每一行。Row Level Security 补上了 grant 这一层：暴露的 schema 里，没有 RLS 的表可以被任何拥有 grant 的角色读写。现有项目上，public 里的新表一开始就把包括 select、insert、update、delete 在内的权限授给 anon、authenticated 和 service_role；文档也说明，并非每个项目都会自动授予。启用 RLS 之后、写出策略之前，用 publishable key 经 API 访问不到数据。在仍然把这些权限授给 anon 的项目上，只添加策略并不会收回 grant。文档写明，如果从未撤销授权，anon 仍有一条插入路径。

secret key 通过带有 bypassrls 的 service_role 角色访问数据库。同一页要求：不要在浏览器里使用 secret key，也不要把它暴露给客户。service_role key 是旧方案，同样要留在服务端。这里有一条不能省掉的限定：secret key 只有在请求没有携带用户 access token 时才绕过 RLS；如果请求带了用户 token，即便客户端用 secret key 初始化，也会按该登录用户的策略执行。无论哪一种，它都不该出现在前端。API keys 文档还写明，secret key 在浏览器里会被按 User-Agent 拒绝并返回 401，但攻击者仍可以从其他工具使用这条密钥。

Firebase 放进客户端配置里的 API key 更不是访问控制。API keys 文档 写明：用于 Firebase 服务的 API key 不负责控制对后端资源的访问。那只能靠 Firebase Security Rules（哪些终端用户能访问）和 Firebase App Check（哪些应用能访问）。Realtime Database、Cloud Firestore 和 Cloud Storage 的数据安全由 Security Rules 执行，而不是靠把这把 key 保密。在 key 已按文档限制在 Firebase 相关 API、并且数据由 Security Rules 与 App Check 保护时，它可以写进代码或已提交的配置文件。

数据能不能被客户端读写，要看规则本身。Firestore 的快速入门把测试模式写成：适合用移动端和 Web 客户端库起步，但允许任何人读取和覆盖你的数据；测完要回到 “Secure your data”。生产模式则拒绝来自移动端和 Web 客户端的全部读写。Avoid insecure rules 说明，在控制台创建数据库或 Cloud Storage 存储桶时，Test mode 是向所有用户开放访问；部署应用之前，要把规则改成真正保护数据的配置。同一页对全开放规则的警告是：绝不要在生产环境使用允许所有人读写的规则集，它会让任何人覆盖整个数据库。如果既没有做用户认证，也没有配置安全规则，猜到项目 ID 的人就可以窃取、修改或删除数据。Cloud Storage 上不带条件的 allow read, write 会让存储桶中的每个文件对任何用户可访问，文档要求在生产环境使用前格外小心。

上传文件如果放在 Amazon S3，公开访问和临时链接要分开看。Block Public Access 在接入点、存储桶、账户和组织这几层提供设置，用来限制对 S3 资源的公开访问。新的存储桶、接入点和对象默认不允许公开访问，但用户仍可能通过存储桶策略、接入点策略或对象权限把它们改成公开；Block Public Access 会覆盖这些策略和权限。官方建议为账户打开全部四项，并在每个存储桶上也打开。应用这些设置之前，先确认应用在没有公开访问时仍然能工作。

需要把单个对象临时交给别人时，用的是 presigned URL。S3 的对象默认是私有的，只有对象所有者有权限访问；所有者可以用自己的安全凭证创建 presigned URL，授予有时限的下载权限。这条 URL 可以放进浏览器，也可以由程序使用。下载和上传说明进一步写明：这种 URL 不必修改存储桶策略，在过期前可以多次使用；用它上传时，如果桶里已经有相同的对象键，S3 会用新对象替换已有对象。文档把它称为不记名令牌：谁拿到，谁就获得签发者权限范围内的访问，因此要妥善保护。

浏览器本地也是一处存放位置。MDN 说明 localStorage 提供的是当前文档所属源的存储，并且会跨浏览器会话保留。OWASP 的 HTML5 Security Cheat Sheet 写明：不要把会话标识放进 local storage，因为这些数据始终可以被 JavaScript 读取；同一源里的对象共享同一份 localStorage，只受同源策略保护。它还建议不要在其中存放敏感信息，一次跨站脚本就可以把这些数据全部偷走。访问令牌不适合放在这里。

因此，浏览器里出现 Supabase 的 publishable key，或用于 Firebase 服务的 API key，本身并不等于把服务端密钥泄露了出去。下一节要查的是另一类值：那些按设计不该离开服务端的密钥，会不会在构建时被写进用户下载的前端包。

二、能跑起来，不代表密钥还在服务端

Vite 的环境变量文档写得很直接：以 VITE_ 开头的变量，会在打包后出现在客户端源码里；为了避免把环境变量意外泄漏到客户端，不要用这个前缀。官方还单独加了一段 “Protecting secrets”：VITE_* 变量不应包含 API 密钥这类敏感信息，因为这些值会在构建时被打进源码。生产环境里，应考虑用后端或 serverless / edge 函数来保管密钥。

Next.js 是同一类机制，只是前缀换成了 NEXT_PUBLIC_。它的环境变量文档说明：加上这个前缀，是为了在执行 next build 时把值内联进发给浏览器的 JavaScript 包；没有此前缀的变量只存在于 Node.js 环境，浏览器读不到。文档还提醒，构建完成后再改这些变量，已经打好的包不会跟着变。

所以，.env 被 git 忽略，只说明仓库里可能没有这份文件。它不能说明：构建工具有没有按前缀规则，把其中一些值写进了静态资源。最近有开发者公开写到，自己用编程助手搭预约应用时，助手为了让浏览器里的聊天功能直接跑通，把密钥命名成了 VITE_ 变量；应用“能用”，密钥也就进了前端包。我没有复现这次检查，但官方文档恰好解释了为什么会出现这种结果：前缀不是笔误，而是构建工具的公开约定。

三、不是所有“密钥”都能放进前端

这里还要再拆一层：不同服务商的“API key”，权限完全不是一回事。

Stripe 把这件事写在密钥类型表里。以 pk_ 开头的 publishable key，官方明确写了 “Safe to expose: Yes”，可以放进前端或分发的应用里；它能识别你的账户、创建 token 或 PaymentMethod，但不能执行创建扣款、读取账户数据这类敏感操作。以 sk_ 开头的 secret key 则相反：权限不受限，官方写明不可暴露，并且已经不建议在新场景里继续用这种无限权限密钥，而是改用可限定权限的 restricted key（rk_...）。restricted key 同样不可暴露。Stripe 的密钥管理最佳实践还强调：secret key 相当于账户的用户名和密码；一旦落到未授权方手里，对方可能发起未授权扣款、读取客户数据，或干扰你的集成。前端该嵌入的是 publishable key，不是 secret key。

OpenAI 没有这种“可以公开的调用密钥”。它的API 密钥安全说明第三条写的是：不要把密钥部署到浏览器或移动应用这类客户端环境。密钥一旦出现在客户端，恶意用户就能拿它冒用你的账户发请求，可能带来意外账单，或危及部分账户数据。请求应始终经过你自己的后端，密钥只留在服务端。

Resend 的密钥处理说明同样要求：不要把 API key 暴露在浏览器或其他客户端代码里；应放在环境变量中，不要提交进版本库，也不要写死在代码里。

因此，不能因为 Stripe 允许把 pk_live_ 放进前端，就推断 OpenAI 或 Resend 的密钥也可以。后者没有“可公开的调用密钥”这一档。前端直接拿这些密钥去调官方 API，看起来是少写了一个后端，实际上是把出账权和发信权交给了每个能打开开发者工具的人。

四、密钥进了前端，账单也不一定有硬上限

密钥暴露之后，损失有多大，取决于对方能用这条密钥做什么，以及你有没有先把费用封顶。

OpenAI 把这两件事写在同一份安全说明里：要为组织或项目设置每月 spend limit，并打开硬性执行（hard enforcement），以限制密钥泄露后的意外费用；只开 spend alert 并不会让 API 流量停下来。更完整的规则在 Spend limits 文档中。提醒和硬上限的效果不同：到了设定金额，提醒只发通知，请求继续成功；硬上限会让受影响的请求返回 429，错误码是 organization_spend_limit_exceeded 或 project_spend_limit_exceeded。文档同时提醒两件容易被忽略的事：硬上限可能打断正常生产流量；执行不是瞬时的，实际花费可能略微超过你设定的数字。此外，平台还会按用量档位给你的组织一个“已批准的月度用量上限”，那是另一套限制，不能当成你自己设定的硬封顶。

换言之，上线前只看“有没有配置费用提醒”，是不够的。提醒解决的是你是否知情，硬上限解决的是账单会不会在你看到通知之前继续往上走。

Stripe 和 Resend 的风险形态不同，但逻辑类似。Stripe 的 secret key 能做的不只是花掉模型调用额度，而是动用支付与客户数据；Resend 的密钥一旦泄露，对方可以直接用你的域名发信。Resend 在泄露后的处理说明里建议：给每个服务单独的密钥，并优先使用“Sending access”而不是“Full access”，这样即使泄露，也能缩小影响面、并在日志里定位是哪一条集成被滥用。

五、发现泄露之后，先作废，再查日志

从代码里删掉那一行，不等于密钥已经失效。前端包一旦被下载，密钥就可能已经不在你的仓库里了。

OpenAI 的建议是：如果认为密钥已泄露，立刻到 API Keys 页面轮换；生产环境还要把新密钥更新到服务端。Stripe 写得更干脆：如果你在源码、配置或流水线里发现了敏感密钥，应假定它已经暴露并被攻破。Resend 则要求先删除已暴露的密钥以停止未授权发送，再根据日志评估损害。共同顺序是：先作废旧密钥，再排查谁用过、用了多少，而不是先观察几天再决定要不要轮换。

作废之后，才谈得上把调用收回服务端。Vite 官方给出的方向就是后端或 edge 函数：浏览器只请求你自己的接口，由服务端读取不含 VITE_ / NEXT_PUBLIC_ 前缀的环境变量，再去调用模型、支付或邮件服务。这里还要补一层，否则你的后端会变成一个不设防的公开代理——任何人都可以通过打你的接口来消耗你的额度。身份校验、按用户或 IP 限流、以及只授予必要权限的受限密钥，都是这层该有的控制。OpenAI 还提供 IP 白名单：开启后，即使请求带着有效密钥，来源不在允许的地址范围内也会被拒绝。

六、上线前更值得先问的几个问题

与其问“应用能不能在浏览器里跑通”，不如先问下面这些问题：

  1. 用户数据实际存放在哪里？把预约记录、聊天记录、个人信息、上传文件分别列出来：自己的数据库、Supabase / Firebase 这类 BaaS、对象存储、第三方服务及其日志，还是浏览器本地存储。
  2. 谁能读写这些数据？用未登录状态，或另一个账号，试一次能不能读到别人的记录。再检查表是否开启了 RLS、策略有没有按用户收紧，Firebase 的 Security Rules 是不是还停在测试模式，对象存储桶是不是公开的。
  3. 构建产物里有没有 Stripe 的 sk_live_ / rk_，以及 OpenAI、Resend 这类本不应出现在前端的密钥片段？只检查仓库和 .gitignore 是不够的，要检查实际发给浏览器的包。
  4. 哪些环境变量使用了 VITE_ 或 NEXT_PUBLIC_ 前缀？这些前缀意味着值会被内联进前端，不能用来放 OpenAI、Resend 或 Stripe 的 secret / restricted key。
  5. 模型调用有没有打开硬性费用上限，而不只是到额提醒？提醒和封顶不是同一件事。
  6. 浏览器是否只持有被官方明确允许公开的值，例如 Stripe 的 publishable key？其余调用是否都经过你自己的后端或 edge 函数？
  7. 你的后端接口本身有没有鉴权和限流？否则密钥虽然离开了前端包，公开接口仍可能变成别人的付费出口。

“能调用”只说明浏览器或服务端发出的请求成功了。“能安全上线”要由数据放在哪里、谁能读写，以及构建产物、密钥类型和费用上限来回答。数据、密钥、费用是上线前要先看完的三层。
