设计系统要让智能体用，先得能被查询，也能被测量

资料核验：2026 年 11 月 11 日 18:01—18:02（新加坡时间），依据 Astryx 官方网站、文档与博客，以及 GitHub 仓库 meta/astryx 当时的公开元数据与许可证文本。产品仍在 Beta，文档和版本会更新，配置细节请以官方最新页面为准。文中的使用规模、组件数量和评测分数均来自官方表述或官方已公布的单次结果，作者没有安装、运行或复现这些工具与评测，也不构成选型背书。

编程智能体已经很会“写界面”了。打开一个对话框，摆一排按钮，再套一层看起来完整的布局，往往很快就能得到能跑的代码。问题是，看起来像那么回事，还不等于它真的用对了你的设计系统。

Astryx 团队在 11 月 3 日的公告 Building for people and agents at Meta San Francisco 里把这点写得很直白：智能体可以生成看起来可信的界面，但看起来可信并不能保证体验过关。他们要讨论的，是如何用清晰的指引、有意义的约束和评测，把生成出来的界面变成人们可以信任的体验。

常见的补救办法，是再往 AGENTS.md 或项目说明里贴一段“请使用我们的组件库，不要乱写 div”。这有用，但它只是一份容易过期的说明书。设计系统如果只为人浏览文档和 Storybook 而写，智能体就只能靠训练记忆、临时爬页面，或者一份与仓库不同步的提示词。模型一旦记错组件名、编造属性，生成结果仍然可以“看起来完整”。

Meta 在 2026 年 6 月 18 日开源的设计系统 Astryx，把这个问题当成一等需求来处理。它现在仍是 Beta。真正值得看的，不是又多了一套组件，而是它把“人和智能体用同一套接口”，以及“用评测而不是口号来证明这一点”，写进了系统设计。

一、先说清楚它是什么

根据 开源介绍 和仓库 README，Astryx 是一套建立在 React 19+ 和 StyleX 上的开源设计系统。官方的说法是：它在 Meta 内部发展了八年，是公司里使用最广、规模最大的设计系统，支撑超过 13,000 个应用，并提供 150 多个无障碍组件、品牌级主题、深色模式、可直接使用的模板，以及一套命令行工具。这些使用规模和组件数量都是官方表述，本文没有独立核实。

仓库目前的规范地址是 https://github.com/meta/astryx；访问 facebook/astryx 会重定向到这里。主分支的 LICENSE 是 MIT，版权声明为 Meta Platforms, Inc.。仓库创建于 2026 年 1 月 9 日，公开介绍发布于 6 月 18 日，此后仍在持续发版。2026 年 11 月 11 日 18:01（新加坡时间）读取 GitHub API 时，最新正式版是 v0.7.13（发布于 11 月 11 日 05:27 新加坡时间），星标为 23,977，这个数字会继续变化。官方页面和 README 都标明它仍处于 Beta。

对使用者来说，还有几条同样来自官方说明的硬约束：需要 React 19 或更高版本；消费端可以导入预构建的 CSS 和带类型的 React 组件，不必先上构建插件或再选一个样式库；主题是一组 CSS 自定义属性覆盖，可以用已有的 Tailwind、CSS Modules 或普通 CSS 通过 className 覆盖样式。仓库还写明，内部虽然用 StyleX 编写样式，但对消费端是不可见的。

这些都是产品事实。更值得追问的是：它所谓“适合智能体”，具体指什么？

二、同一套接口，人和智能体一起用

Astryx 的介绍文说得很清楚：设计系统过去主要是写给人看的；随着越来越多代码由智能体编写，必须重新思考设计系统的结构，以及它该扮演的角色。它声称自己是从一开始按“可被智能体操作”来做的，而不是事后给现有系统打补丁。

落在工具上，这个选择首先体现在命令行。CLI 文档把命令行称为人和机器共用的主界面：组件文档、设计令牌、页面模板、主题工具和升级用的代码修改，都可以通过终端命令、带类型的 JSON 接口或编程导入来访问。站点上的 llms.txt 写得更直接：文档站上的组件说明、属性、变体、令牌、模板和设计规则，同样可以通过 CLI 以适合智能体阅读的形式获得；与其爬这些页面，不如直接用命令行查询。

这和“再写一份给模型看的说明书”不是一回事。页面、命令行和 JSON 接口如果指向同一份来源，智能体查到的就更接近人正在看的文档。CLI 还提供 astryx manifest --json：一次调用就能得到命令、参数、选项、是否支持 JSON，以及各命令会返回的类型。官方把它比作命令行的 OpenAPI 说明，并写明这份清单来自真实的命令定义，有漂移测试守门。出错时，文档要求按稳定的 code 分支处理，不要解析会改写的人类可读错误句。

项目里要让智能体按同一套约定工作，官方给出的入口是 Working with AI：运行 npx @astryxdesign/cli init --features agents，根据当前安装的项目生成上下文，默认写入 AGENTS.md。生成内容会教智能体在写界面之前走三步：先用 build 找到最接近的页面模板，再用 template 搭出骨架并替换内容，最后用 component 读取所用组件的属性和例子。依赖升级后，可以用 upgrade 检查并刷新这段由 Astryx 管理的内容，避免手册和仓库各写各的。

它也提供 MCP 服务，地址是 https://astryx.atmeta.com/mcp。官方文档写明，这个服务目前暴露两个工具：search 用来发现组件、文档主题和模板，get 用来取回带属性、用法和示例的完整文档；搜索用的是与组件文档相同的关键词索引。换句话说，MCP 是同一套资料的查询入口，并不是另一份平行文档。

这里有一个很容易踩的坑，官方在 CLI 文档和 llms.txt 里都强调过：一次性运行时要用带作用域的包名 @astryxdesign/cli。在把 CLI 安装为依赖之前，不要运行未加作用域的 npx astryx，因为这个名字会解析到另一个无关的 npm 包。官方还建议在 package.json 里写下指向本项目 CLI 的 script，让智能体执行 npm run astryx -- component --list，而不是去猜 node_modules 里的二进制路径。

三、口号不够，得拿来测

如果只看到“适合智能体”，这套叙事并不稀奇。Astryx 更少见的地方，是它愿意把这句话拿去测，而且并不回避测输的时候。

仓库 README 把这条写成原则：约定要靠测量获得，而不是靠断言；对结果保持松手，并在新情况证明它错了的时候再回头看。2026 年 7 月 27 日，Cindy 和 Ernest 在博客 Vibe Test 里公开了他们的做法。

他们先做过一轮“是否按我们希望的方式使用了 Astryx”的评测，后来认为这不够公平：它默认 Astryx 就是正确答案，也无法和别的方案比较。于是改成目标中立的评测，用同一套分析去看 Astryx、Tailwind、shadcn 和原始 HTML，打分看的是任何好的输出都应具备的属性，而不是“像不像我们”。提示词被要求写用户体验，而不是点名具体组件，例如说“做一个用户可以逐条展开问题的 FAQ 页面”，而不是“用可折叠列表做一个 accordion”。评测智能体不能携带已有的项目记忆；执行的子智能体要隔离上下文；最后由另一个智能体当评委，避免自己给自己打分。系统评测看正确性、无障碍、代码质量、效率、可维护性和设计，其中设计维度按渲染截图对照参考图评分，官方写明这一项仍在完善中。

他们把这套测试做成每晚定时运行的“守夜”，在四种配置上跑同一组提示词。博客公布了两个具体夜晚，而不是一个笼统均值。2026 年 7 月 10 日是他们所说的好夜晚，总分是：Astryx 98，Astryx 加 Tailwind 97，基线（shadcn/Tailwind）95，原始 HTML 82；当天 Astryx 的正确性、无障碍、代码质量和可维护性都是 100，效率是 88，设计项仍标为进行中。但他们紧接着公布了 6 月 28 日这个糟糕的夜晚：Astryx 总分降到 77，把当晚输给了基线；其中正确性只有 2，无障碍 98，代码质量 99，效率 91，可维护性 96。原因是智能体在一部分提示上捏造了导入路径和属性名，一个类别拖垮了整晚。

更关键的是他们随后写下的那句：在完整记录里，基线实际上赢了多数夜晚；他们并不总是领先，把记分板公开，正是为了没法把这一点藏起来。智能体不是确定性的，所以有些夜晚会跑偏。评测失败后，另一班“守夜”会阅读失败的提示、给失败分类，并在能够修复时针对文档或命令行开出变更。官方也提醒，不能只追单个糟糕夜晚里的偶发波动，而要找重复出现的模式，并用复现来证明。

这两晚的分数是 2026 年 7 月博客里公布的单次结果，不能外推成当前版本、当前模型或你自己项目里的表现。它真正提供的，是一种态度：所谓“智能体可以用”，必须能在朴素提示、对照方案和公开失败记录里被检查。看起来完整的界面，过不了这一关，就不算过关。

四、就算不采用 Astryx，也可以先问这几个问题

不是每个团队都该换到 Astryx，它仍是 Beta，还绑定 React 19+。但任何准备让编程智能体改界面的组件库，都可以把上面的设计选择当成检查清单，而不必先接受它的品牌和主题。

第一，智能体怎样查到“现在”的组件，而不是训练数据里的旧印象？如果唯一入口是给人看的网页，模型就很容易靠记忆补全，也容易编造属性。一套可以返回结构化结果、带稳定错误码、并能从当前安装版本生成说明的查询接口，比再维护一份平行提示词更接近真相。

第二，人和智能体是否在用同一份来源？如果官方文档是一套，给模型的摘要是另一套，后者通常会过期。Astryx 的做法是让命令行读取与文档站相同的资料，再由 init 和 upgrade 把项目内的智能体说明保持为仓库的派生结果。

第三，你有没有用朴素任务去测，而不是只看演示？提示词一旦写成“请使用某某 Accordion 组件”，测到的往往是遵从性，不是发现能力。对照至少一种常见替代方案，并接受自己会输，才知道这套系统是真的更好，还是只是更眼熟。

第四，定制会不会逼着智能体去分叉组件源码？如果换个颜色或圆角就要复制整份实现，智能体和人一样会制造无法升级的分叉。把可变的部分收在令牌和 CSS 变量里，把行为、无障碍和结构留在系统里，分叉才会成为例外，而不是默认路径。

这些并不是 Astryx 的专利。它们是在问：你的设计系统有没有把智能体当成真实的使用者，而不是事后再补一套话术。

五、一份可以直接用的最小清单

如果你已经在让编程智能体写页面，可以从这几件事开始：

  1. 先给查询入口，再放开写代码。 至少准备一种不靠爬文档站的方式，让智能体按名称或意图查出组件、属性和示例。能返回稳定的错误码更好，因为它查错时才有办法自我纠正。
  2. 让项目里的智能体说明从仓库生成，并在依赖升级后刷新。 不要长期手写一份和组件库脱节的“AI 指南”。
  3. 用项目内的命令来调用工具。 不要依赖智能体去猜全局命令或 node_modules 路径；像 Astryx 提醒的那样，未加作用域的包名还可能指向完全无关的软件。
  4. 用朴素的产品任务做对照评测。 不要在提示里点名组件，至少和一种现有方案比，记下失败类别。一次好看的演示，说明不了稳定性。
  5. 把“看起来完整”和“用对了系统”分开验收。 页面能渲染，只是第一步。还要看它有没有编造组件、绕开令牌、把本该用组件的地方写成一堆无语义的包装元素。

设计系统要面向智能体，并不是把原来给人读的文档再摘要一遍。更要紧的是：智能体能否查到和人相同的、仍然有效的约定；这些约定能否在对照评测里被证伪。Astryx 提供的不是一个已经赢了的分数，而是一套把这个问题公开摊开的做法。分数会变，版本会变，但这个问题不会消失。
