资料核验：2026 年 11 月 19 日约 17:50—18:00（新加坡时间），依据 yikart/AiToEarn 当时的 GitHub 元数据、MIT 许可证、README 与默认配置，以及官方文档站的 Docker 部署、通过插件发布、贡献指南和新手指南。仓库仍在更新，星标、默认状态和文档都会变化，细节请以各官方页面最新文本为准。本文只比较公开写明的产品说明与开源仓库里的默认配置，作者没有安装、启动或测试这些服务，也没有注册、付费或向任何平台发布内容，不构成选型、部署或采购建议。

“一站式内容变现”是现在很好卖的一句话。打开一个星标很高的开源仓库，最上面往往写着：创作、发布、互动、变现，再列一排国内和海外平台。读到这里，人很容易把三件事当成一件事：产品宣称覆盖哪些能力，自托管默认能启动哪些模块，以及把内容真正发到某个平台还要再配什么。

这和本博客谈按结果收费要先读懂“结果”怎么算是同一类问题，只是对象从计费口径换成了开源项目的能力边界。它也和数字人直播要分清“能推流”和“能无人值守”类似：产品说明里的场景，不能直接当成已经交到你手里的默认能力。

一、宣传页交出的，是一条完整变现链路

以目前讨论很多的开源项目 AiToEarn 为例。2026 年 11 月 19 日 17:53 左右用 GitHub 接口读取的元数据是：28,391 星，4,746 个 fork，许可证为 MIT，仓库主页指向 aitoearn.ai。最近一次代码推送在 2026 年 11 月 16 日 18:34（新加坡时间），最新正式标签是 2026 年 6 月的 v2.5.0。星标会继续变化，请以仓库页面当时的数字为准。

README 把自己定位成“一站式 AI 内容变现平台”，并把能力写成四块：Monetize、Publish、Engage、Create。变现部分列出 CPS、CPE、CPM 三种按结果结算的模式；发布部分写的是“一键将内容分发到 14+ 主流平台”；互动依赖浏览器插件；创作则调用各类视频和图片模型，并支持批量生成。平台清单也很明确——国内写的是抖音、小红书、快手、B 站、视频号、公众号，海外写的是 TikTok、YouTube、Facebook、Instagram、Threads、X、Pinterest、LinkedIn。

这些都是官方产品说明。它们说明项目想覆盖的范围，但不能单独证明：自托管的开源栈已经包含全部模块，默认配置已经打开了这 14 个平台，或者作者在这些平台上跑通了发布。把 README 的项目符号读成“clone 下来就能用”，是这类项目里最常见的误判。

二、开源导航里，没有单独的“任务市场”

先看变现。README 把“在平台出售内容以完成商家推广任务”写成最核心的目标，更新日志里也把“内容交易市场上线”写在 2026 年 3 月的 v2.1。官方新手指南确实在讲创作者如何接任务、商家如何按互动量或播放量找人推广，并给出结算口径。这些文字出现在云端产品的帮助文档里，指向的是 aitoearn.cn 和 aitoearn.ai。

再看当前开源前端的导航配置 routerData.tsx。文件开头的注释写的是“开源版保留导航项”。实际列出的入口是：内容管理（草稿箱）、AI 发布、任务历史、发布/账号，以及 Agent 资产。这里没有单独的“任务市场”或“变现”页面。

因此，更稳妥的读法是：变现市场主要是官方云端产品的能力；不能只根据 README，就断言自托管开源栈已经完整包含任务接单和结算。开源仓库交出来的，首先是一套内容管理和发布的骨架，而不是把云端市场上的买卖关系一并搬到你的机器上。

三、平台清单要对照默认配置，而不是 README 的项目符号

发布能力也要拆开看。自托管后端的默认配置里，平台并不是铁板一块，至少有三种状态。

第一种是 available。快手、B 站、小红书、视频号，以及 README 列出的多数海外平台，默认都是这个状态。但这只表示配置层没有把它们藏起来。这些项的 OAuth 凭证在样例配置里是空的，或只是占位符。官方部署文档写得很直接：不配 Server Relay，就要自己去十几个平台申请开发者账号；配了 Relay，则是借用官方站点的凭据来完成授权。也就是说，状态写成“可用”，并不等于开箱就能授权、更不等于已经能发。

第二种是 hidden 或 coming_soon。抖音在默认配置里是 hidden；微信公众号是 coming_soon，帮助文档里还标成 beta。后端还出现了 README 宣传清单里没有的 Google Business，默认同样是 hidden。把这三项从“宣称支持”直接抄进“默认能用”，并不符合当前配置。

第三种差异出现在浏览器插件。官方插件发布文档写明：插件可发布到小红书、微信视频号和抖音，并复用当前浏览器里的平台登录态，网页不必复制 Cookie。可是开源前端当前的 PLUGIN_SUPPORTED_PLATFORMS 常量，只包含小红书和视频号。文档覆盖范围，和此时开源前端写死的常量，并不是同一张清单。

所以，“支持某个平台”至少有三层含义：出现在宣传清单里，出现在默认配置的状态字段里，以及是否已经具备 Relay、自备开发者凭证或可用的插件通道。只看第一层，会高估开箱体验。

四、“三条命令”之前，先要有一组自己的密钥

README 把 Docker 部署写成“3 条命令搞定”，并提醒启动前按 DOCKER_DEPLOYMENT_CN.md 配置必填认证密钥。但在 2026 年 11 月 19 日的 main 分支上，这个文件并不存在。完整步骤在官方文档站，而不是仓库根目录的那份旧说明。

文档现在要求：docker-compose.yml 和两份 config.yaml 不再内置认证密钥默认值，启动前必须自己生成并填写 auth.secret、auth.internalToken，以及 server 侧与之对齐的 aiClient.token。缺少 JWT_SECRET，Compose 会直接拒绝启动；密钥彼此不一致，则可能出现页面能打开但无法自动登录，或调用 AI 时返回 401。界面启动之后，仍要再配 Server Relay 才能较省事地做平台授权；不配 AI Relay、也不填自备的模型服务商密钥，创作和生成类功能也还不能用。

这类文档漂移不只这一处。README 的 Node 徽章仍写 20.18.x，后端 .nvmrc 和 Docker 镜像线索已是 24；README 写明暂不接受外部 Pull Request，文档站的贡献指南却仍按 Fork 后提 PR 来写，并指向仓库里并不存在的 project/backend/README.md。它们不会让“三条命令”立刻失败，但提醒同一件事：要以当前文档站和当前配置为准，不要把过时路径或宣传省略当成完整步骤。

需要再次说明：以上判断都来自公开文档和仓库文件，作者没有执行 docker compose up，因此这不是一次运行时验收。

五、更有用的问题，不是“能不能一键部署”

把宣传清单和默认配置放在一起，分界其实比较清楚。

开源栈能提供的，是一套可自托管的内容管理、账号和发布骨架，以及通过官方 Relay 或自备开发者凭证去接通平台的路径。云端产品另有任务市场和按结果结算等能力，这些主要写在官方站点的帮助文档里。默认配置里“可用”的平台，仍要补齐授权；宣传清单里有、但状态是隐藏或即将推出的平台，更不能当成开箱即用。插件文档覆盖的平台，也不自动等于当前开源前端常量里的平台。

因此，决定要不要自托管之前，下面四个问题比“哪条命令能拉起容器”更有用：

  1. 你真正需要的是任务市场和结算，还是本地的内容生成与发布？前者目前更应到官方云端产品里核对，后者才是开源导航里能直接看到的部分。
  2. 目标平台在默认配置里是 available、hidden 还是 coming_soon？如果是前者，你准备用 Server Relay，还是自己申请开发者凭证？
  3. 若依赖浏览器插件，官方文档列入的平台，和当前开源前端常量是否一致？
  4. 你是否已经按文档站生成并对齐了认证密钥，而不是还在找仓库里已经不存在的部署说明？

“宣称支持”只说明产品想覆盖的范围。“默认可用”要由开源导航、默认状态和授权方式来回答。先读懂这条分界，再决定用云端产品还是自托管，才不至于把 README 上的 14 个平台，误当成 clone 下来就已经接通的渠道。
