资料核验：2026 年 11 月 12 日 17:58（新加坡时间），依据 Telegram 官方 Bot API 更新日志、Telegram Widgets 开发文档，以及官方仓库 TelegramMessenger/widget-sandbox 的公开文档。该功能正在分阶段开放，限制和接口可能变化，请以官方最新页面为准。作者没有用真实机器人部署或测试过文中的代码，示例只用于说明接口形态。

做智能体产品的人，很容易默认一条路线：先有一个对话框，再在对话框旁边做一个控制台、一个网页、一个小程序。用户在聊天里说需求，真正确认、查看进度、点按钮的地方却在另一个界面里。

Telegram 在 2026 年 11 月 9 日发布的 Bot API 10.4，提供了另一种思路：让机器人直接发一条“会动的消息”。官方叫它 widget，下文称“小组件”。它不是一个缩小版的网页应用，而是一段嵌在消息气泡里的、离线运行的极小程序。

这件事本身是一个平台的新功能，但它背后的设计取舍，对所有在聊天里做智能体的人都有参考价值：界面代码一旦发出就固定，状态只能由后端写，前端只能“请求”。

一、它到底是什么

按官方文档的描述，小组件有几条硬约束：

  • 一份自包含的 HTML。 CSS 和 JavaScript 都要内联，图片只能是 data: URL 或内联 SVG。源码最多 32768 字节，服务器用 zlib 压缩后不能超过 4096 字节。
  • 完全离线。 fetch、XMLHttpRequest、WebSocket 等网络接口都会抛错，外部脚本、字体和图片一律不加载，也不能跳转页面。
  • 不在浏览器里跑。 脚本运行在 QuickJS 这个小型 JavaScript 引擎里，不是 WebView。客户端检查脚本对页面做的每个改动，只绘制合规的部分，因此在 iOS、Android、桌面和网页版上表现一致。
  • 原生外观。 聊天主题色以 CSS 变量提供，没写样式的 <button> 会画成客户端自己的按钮。没有键盘输入，输入框、下拉框都会被移除。
  • 代码固定，状态可变。 HTML 发出后没有任何方法能替换它；会变的只有状态，而且只有机器人能写。

最后一条最关键。状态分两种：chat_data 绑定一条消息，只在当前聊天可见；public_data 是随小组件显示在各处的共享状态。小组件只能读取状态、监听变化，不能自己改。它唯一的出口，是调用 TelegramWidget.request(data) 向机器人发一个 1—64 字节的请求；机器人用 answerWidgetQuery 在 15 秒内回复，回复最多 1024 字节，只给发起请求的那个小组件。要改状态，机器人得另外调用 editMessageWidgetData。

这和 Telegram 已有的 Mini App 是两回事。官方文档专门做了对比：Mini App 是你托管的网页，在 WebView 里按需打开，可以联网、可以用键盘；小组件是消息的一部分，随聊天滚动一直可见，没有网络。复杂功能，官方建议仍然用 openTelegramLink 跳到机器人或 Mini App。

二、为什么这对智能体有意思

智能体在聊天里的回复，大多是文字。文字适合解释，不适合让人做决定。一个需要确认的操作，比如“按这个方案派单吗”“这笔付款确认吗”，用户往往要回一句“好”，再由模型去理解这句“好”指的是什么。

小组件的模型恰好把这一步结构化了：

  1. 智能体在后端生成一张卡片。 卡片上写清楚方案、金额、对象，带一个“确认”按钮。
  2. 按钮只发一个短请求。 比如 approve:1042。小组件本身没有权限做任何事，也拿不到网络。
  3. 后端决定是否执行。 收到请求的是机器人，它去核对这个用户是谁、这单是否还有效，再决定执行，然后把卡片状态改成“已确认，执行中”或“已过期”。

这正是我在《给编程智能体放权之前，先想清楚它在哪里必须停下》里说的那种停点：人确认的是一个具体、可读的对象，而不是一段自由文本；真正有副作用的动作，留在能做校验和审计的后端。小组件的设计把这件事从“建议”变成了平台约束：前端想绕也绕不过去，因为它根本不能写状态、不能联网。

付款流程更能看出这种分工。官方文档写明，小组件可以通过 Telegram 内置的 TON 钱包请求付款或签名：点击时请求机器人，机器人返回一笔新生成的交易，小组件再交给钱包窗口，由用户在气泡之外的系统窗口里看到金额和收款方并确认。之后机器人收到交易哈希，文档要求它到链上核对发送方、收款方、金额和结果，而不是只凭哈希就相信。即使你用不到钱包，这个顺序也值得照抄：前端发起，后端出具，系统界面确认，后端再核对结果。

三、几个容易忽略的限制

一个新功能刚出来，最容易被高估。官方文档里有几处限制，决定了它现在能做什么：

  • 生产环境只开放了一部分。 目前正式环境里，小组件只能出现在用户与机器人的私聊中，而且机器人发出的小组件消息自动受保护、不能转发。群组、内联模式、转发，都还只在测试服务器上可用。想做“群里一起投票”的智能体，眼下还不能上线。
  • 请求有频率上限。 每个用户对每个机器人，5 秒内最多 5 个请求，后台请求也算在内。后台请求只在私聊原消息可见时发出，出现时一次，之后最多每 5 秒一次。它适合刷新眼前这张卡，不适合当成实时通道。
  • 状态更新算发消息。 一次 editMessageWidgetData 计为机器人的一条发送；共享小组件每秒最多改一次。很多人同时操作时，文档建议在自己这边合并，最多每秒写一次。
  • 没有无障碍语义。 当前版本里 aria-* 属性保留但不生效。文档建议把关键信息也写进消息说明文字（caption），不支持小组件的客户端也会显示这段文字。
  • 代码和共享状态要当成公开的。 文档明确说：转发会把代码和共享状态带到任何聊天；在群里，聊天状态对所有成员可见；不要往小组件里放任何秘密。

另外要注意，它是 Telegram 一家的协议。官方开源了 widget-sandbox（截至核验时最早的标签是 v0.1.0，文档建议固定使用 v0.1.1 这样的标签而不是分支），但这不等于出现了一个跨平台标准。

四、即使不用 Telegram，也可以借鉴的四条

我更看重它背后的接口设计，而不是某个平台的新按钮。把它抽象一下，任何在对话里做智能体的产品都可以对照：

  1. 让确认对象可见、可读。 需要人拍板的地方，给一张写清楚“做什么、对谁、多少钱、何时过期”的卡片，而不是让模型去理解“好的”“行”。
  2. 前端只发意图，不持有权限。 按钮发出的是短小、可枚举的请求，比如 approve:<id>；后端负责鉴权、校验和执行。即使界面被篡改，能做的也只是“请求”。
  3. 界面代码发出后不变，变化都走状态。 这样历史消息里的卡片不会因为你改了模板而突然变成另一套逻辑；要新布局，就发新消息。审计时，看到的就是当时用户看到的。
  4. 每一种结果都要画出来。 文档的设计指南要求展示“发送中”、机器人的回答和每一种错误码。智能体的操作尤其需要：超时、过期、被拒绝，都应该有明确的状态，而不是让卡片停在一个看似还能点的样子。

结语

智能体的界面，不一定非要是一个单独的应用。很多时候，用户需要的只是一张能看懂、能点一下、点完能看到结果的卡片，而且这张卡片不能越权。

Telegram 这次给出的答案很克制：4KB、离线、不能输入、不能自己改状态。正是这些限制，让它更适合承载“人确认、后端执行”这一步。它现在还只在私聊里正式可用，离成熟还远；但“代码固定、状态归后端、前端只发请求”这条原则，今天就可以放进你自己的智能体产品里。
