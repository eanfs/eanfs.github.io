给编程智能体放权之前，先想清楚它在哪里必须停下

资料核验：2026 年 11 月 10 日约 18:10（新加坡时间），依据 Claude Code 与 OpenAI Codex 官方文档、hexo-deployer-git 源码，以及 Sergey Kuhne 的原文。产品文档会更新，配置细节请以官方最新页面为准。文中“本博客的发布”一节是真实发生的流程，其余部分是公开资料分析，不代表对任何工具的安全背书。

用 Claude Code、Codex 这类编程智能体干活久了，很多人会遇到一个反直觉的问题：智能体越能干，人反而越累。

Sergey Kuhne 在 11 月 8 日的文章 How I’m fighting the AI Brain Fry 里描述得很准：一个任务等回复时开第二个，第一个回来又需要澄清、追问和一个支线任务，不知不觉就在 20 个终端线程之间来回跳，脑子装不下所有上下文。这篇文章在 Hacker News 上拿到了 300 多分。

他的解法后面会讲。先说一个更底层的问题：我们之所以要盯着这么多线程，往往是因为没想清楚哪些动作可以让智能体自己做，哪些必须停下来等人，以及这条线到底由谁来守。

一、写在提示词里的规矩，不是权限

很多人给智能体立规矩的方式，是在 CLAUDE.md、AGENTS.md 或系统提示里写“不要推送到 main”“不要删文件”。这有用，但它不是边界。

Claude Code 的权限文档把这点写得很直白：权限规则由 Claude Code 执行，而不是由模型执行；提示词和 CLAUDE.md 里的说明只影响 Claude 想做什么，不改变 Claude Code 允许做什么。要真正授予或收回能力，得用权限规则、权限模式或 PreToolUse 钩子。

OpenAI 的 Codex 安全文档用了另一套词，意思一样，把控制分成两层：

  • 沙箱模式：技术上能做什么，比如能写哪些目录、能不能联网；
  • 审批策略：什么时候必须停下来问你，比如要离开沙箱、要联网、要运行信任列表之外的命令。

换句话说，“让模型自觉”是第三层，是最软的一层。真正靠得住的，是工具本身的限制和外部系统的权限。

二、按“能不能撤回”给动作分级

与其逐条列禁令，不如先按后果把动作分级。一个实用的分法是看它能不能撤回、影响是否出了你的工作区：

级别 典型动作 建议处理
只读 读文件、搜索代码、查文档 放开
工作区内可撤回 改文件、跑测试、在分支上提交 在版本控制里放开，事后看 diff
越出工作区 改工作区外的文件、联网、装依赖 需要时再批
对外且难撤回 推送共享分支、发布上线、发消息、付款、删数据 必须人来拍板

两家工具的默认值大体就是按这个思路设的。Codex 在受版本控制的目录里推荐 Auto 预设（工作区可写、按需审批），能在工作区内读、改、运行命令，但要改工作区外的文件或联网时会请求批准；即使在可写的工作区里，.git 目录也被保护为只读。Claude Code 的默认手动模式下，读文件不需要批准，Bash 命令和改文件需要批准。

这里有两个容易踩的坑，都写在官方文档里。

第一，命令文本规则不是安全边界。 Claude Code 的规则按“拒绝、询问、允许”的顺序判断，拒绝优先。你可以写一条拒绝 Bash(git push *) 的规则，但文档明确说明，它拦得住 git push origin main，拦不住 git -C . push origin main 这种换了写法的调用。真正要硬性限制文件和网络访问，需要沙箱或钩子。

第二，“一路放行”的模式要放在隔离环境里。 Claude Code 的 bypassPermissions 和 Codex 的 --dangerously-bypass-approvals-and-sandbox（别名 --yolo）都会跳过审批，两份文档都提醒只在容器、虚拟机这类隔离环境中使用。

所以最后一级“对外且难撤回”的动作，最好别只靠本机规则拦，而是让外部系统本身就不给这个权限：生产部署的凭据不放进智能体的环境，受保护分支要求审查后才能合并。Kuhne 的做法也是这样：智能体会做研究、构建、测试，碰到敏感代码就在分支上做并先问，但从不部署到生产，那一步留给他自己。

三、一个真实例子：这个博客的发布

这个博客最近两篇文章，都是由云端编码代理按“源稿进源仓库、构建、发布到站点仓库”的流程处理的。中间有两次停下，正好说明分级为什么重要。

第一次停下，是因为发现默认部署命令会强推。 博客用 Hexo 搭建，常规发布命令是 hexo deploy，背后是官方插件 hexo-deployer-git。看它的源码可以发现两件事：推送时固定带 --force；如果本地没有 .deploy_git 目录，它会先 git init 建一段全新的历史。在每次都是全新环境的云端任务里，这两点加在一起，意味着“发一篇新文章”实际执行的是“用一段新历史强行覆盖整个站点仓库”。

这在人手动发布、本地一直留着 .deploy_git 的时候不一定出事，但对智能体来说，它就从第二级动作变成了第四级。正确做法不是让智能体自己判断“应该没问题”，而是停下来，换成在站点仓库现有历史上做普通增量提交、普通推送，并且只改本篇需要的页面和索引。

第二次停下，是因为推送被拒绝了。 改成普通推送后，站点仓库返回了 403：代理没有该仓库的写权限。这时候“绕过去”的选项其实很多，比如换一个有权限的凭据、改远程地址。代理没有这样做，而是停下来报告；授权开通后第一次重试仍被拒绝，它也照样停下，直到写权限按正常流程真正生效，才完成发布。

事后看，这次 403 恰好是外部系统在守最后一道线：智能体本地有多少规则都不如“没有这个权限”可靠。

四、把“等你拍板”的事收进一个地方

分级解决了“哪些要停”，但停下来的事多了，人还是会被打断。Kuhne 原文里最值得抄的，是他处理这些停顿的方式：

  1. 队列放在 git 里。 每张工单是仓库里的一个 markdown 文件，就放在相关代码旁边，看板状态是一次提交快照。重要的东西不留在聊天窗口里，也不留在脑子里，会话断了队列还在。
  2. 只有一个“负责人收件箱”。 一个脚本读完整个看板，按优先级只列出等他判断的事：审这个改动、回答这个问题、权衡这个取舍。
  3. 结论写回工单。 他用一个每轮从 git 重建的页面来阅读改动和理由，但页面只是查看器，结论写回 git 里的卡片。
  4. 一次处理一件，处理完就关掉。 拿一件、载入上下文、做决定或要求动作，然后放回队列。他说“关掉”是整个方法的关键：上下文随工单一起关闭，下一件才能专注。

他也很坦率：这样做仍然累，只是不再分心和迷失；难点在于把上下文整理得一分钟就能看懂，以及防止工单因为等他裁决而无限卡住。

把这套做法和上面的分级结合起来，就得到一个比较健康的分工：前三级动作让智能体自己在分支上做完、留下证据；第四级动作统一进入收件箱，每一条都带上改了什么、证据是什么、能不能撤回、不批会怎样。人不再盯着 20 个线程，只在少数真正需要判断的地方出现。

五、一份可以直接用的最小清单

如果你准备让编程智能体接手更多工作，可以从这几件事开始：

  1. 列出“必须人来做”的动作：推送受保护分支、生产部署、对外发消息、付款、删数据。一般不超过五六类。
  2. 让外部系统守住这些动作：智能体环境里不放生产部署凭据，受保护分支要求审查，CI 通过才能合并。
  3. 本机规则做第二层：用工具的权限规则把这些动作设为询问或拒绝；需要硬限制时加沙箱或钩子，别只靠命令文本匹配。
  4. 审一遍默认脚本：像 hexo deploy 这种用了多年的命令，可能藏着强推、重建历史这类在新环境里才暴露的行为。交给智能体之前，先读一下它实际执行了什么。
  5. 遇到拒绝就停：权限被拒、检查失败时，让智能体报告实际状态，而不是换凭据、改配置去“想办法”。
  6. 所有停顿进一个收件箱：每条带上下文和可选项，一次处理一件，结论写回记录。

结语

给智能体放权，真正难的不是“开不开自动模式”，而是提前想清楚它在哪里必须停下，以及这条线由谁来守。

提示词能让智能体更守规矩，工具权限能让它犯错的范围更小，而外部系统的权限才是最后的边界。把这几层摆对，再把所有需要人判断的事收进一个地方，智能体才会真的替你省力，而不是让你在 20 个线程之间疲于奔命。
