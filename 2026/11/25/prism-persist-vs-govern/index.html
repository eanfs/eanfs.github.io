资料核验：2026 年 11 月 25 日约 17:55—18:25（上海时间），依据 Mirantis 2026 年 11 月 24 日的开源公告、Mirantis/prism 当时的 GitHub 元数据、仓库内 LICENSE、README.md，以及 docs/README.md、docs/heartbeat.md、docs/scheduled-tasks.md、docs/webhooks.md、docs/agent-identity.md、docs/configuration.md、docs/tools.md，并对照当时能读到的 src/lib/tool-risk-gate.ts。仓库、星标、默认模型和文档都会更新，计数与配置请以各官方页面与仓库文件的最新文本为准。本文只比较这些公开文本当时怎么写，作者没有安装、运行或测试该软件，不构成选型背书、安全审计或部署结论。

产品介绍里越来越常见一句话：智能体在对话结束后还能继续干活。听的人往往把它理解成另一句：既然它会自己醒来做事，我写下的规则也就能把它按在原处。这是两件事情。

2026 年 11 月 24 日，Mirantis 把 Prism Agent 以 Apache 2.0 许可证开源，宣传点正是“对话结束后继续工作”：目标会跨轮次推进，任务能按你设的时间跑，做完再通知你。这和本博客谈给编程智能体放权之前，先想清楚它在哪里必须停下有关，但本文不展开通用的权限分级，只看这一份刚公开的文档，怎样把“能定时醒来并调用工具”和“能按规则无人值守”分开。它也和数字人要上直播平台，先分清“能推流”和“能无人值守”类似：能持续运行，并不自动等于可以放心离开。

一、“对话结束后还能继续跑”，在文档里指什么

2026 年 11 月 25 日约 18:00，用 GitHub 接口读取 Mirantis/prism 的元数据：公开仓库，主要语言 TypeScript，许可证 Apache-2.0，描述为 “Prism Agent Harness”。当时星标 18，fork 0，open issues 计数为 16（按 GitHub 惯例可能包含未关闭的 pull request）。仓库创建于 2026 年 5 月 21 日 16:05（上海时间）；当时 main 上能读到的最新提交是 a9bc7940a9a5（2026 年 11 月 23 日 21:18，上海时间）。GitHub Releases 当时列出的较新标签是 v2026.11.19151733（发布于 2026 年 11 月 19 日 23:29，上海时间），main 上还有此后的提交，讨论能力时应以仓库文件的最新文本为准，不宜把某一天的标签当成已经冻结的产品版本。星标会继续变化，请以仓库页面当时的数字为准。

仓库根目录的 LICENSE 是 Apache License 2.0 文本，与 GitHub 识别到的 SPDX 标识一致。官方公告和 README 都把这套软件写成面向公司的独立智能体：由 Lens 的 Kubernetes IDE 内置助手发展而来，由 Mirantis 自己使用；安装方式包括一行脚本、容器镜像 ghcr.io/mirantis/prism，以及 Mirantis Agent Platform。文档还写：它是自包含的，一个运行时带着嵌入式数据库，不依赖外部服务，硬依赖只是一个大模型服务商。这些是项目自己的说明，不是第三方评测。

所谓“对话结束后继续工作”，公开文档里主要是这些可核对的机制，而不是一句形容词：

  • 目标（Goals）：用 /goal 放下一个后台目标，智能体会跨轮次推进，直到完成、暂停或被停下。
  • 定时任务：可用自然语言（例如 “every weekday at 9am”）或 cron。一次性任务跑完会删除自己；周期性任务会记下上次运行、下次运行和连续错误次数，并且在重启后仍在。任务触发时会带上完整工具集去执行那条指令；也可以把送达目标设成 None，只跑、不发消息。
  • 心跳（Heartbeat）：按心跳文档里的检查项周期性醒来，默认每 8 小时一次，最短可设到 1 分钟。文档写明：只有检查发现需要你知道的事情才会发消息，没有新发现就保持安静；下一次心跳会看到此前发过的内容，只为新发现或变化再发。连续出错时会退避并停掉循环，以免在坏掉的检查上空转；额度用尽这类错误被单独当成暂时失败，不会计入那条连续出错计数。
  • Webhook：在 Web UI 打开接收后，外部系统可向 3004 端口推送事件；发送方用共享令牌或 HMAC 证明自己。接收是异步的，避免调用方一直等到智能体跑完；每个订阅的运行会按到达顺序串行执行。
  • 记忆与恢复：长期记忆可跨对话保留，公告还写：已接受的工作在进程重启后会接着做。原生安装会把运行时注册成 launchd、systemd 或 Windows 计划任务，也就是把“继续跑”做成了后台服务，而不只是聊天窗口还开着。

它能做的事情同样写得很宽：执行命令、读写文件、把编程任务交给 Claude Code 或 Codex 并跟到结束、阅读公开网页；在容器镜像里还可以操作自己的桌面和浏览器。模型方面，README 写的默认主循环是 Claude Opus 5，分类门闩是 Claude Haiku，向量嵌入在 Bedrock 上默认用 Amazon Titan v2；docs/configuration.md 里 Bedrock 的默认标识分别是 global.anthropic.claude-opus-5-5、global.anthropic.claude-haiku-5-5 和 amazon.titan-embed-text-v2:0。LLM_PROVIDER 当时支持 bedrock（默认）、azure、bedrock-mantle、openai、chatgpt、openrouter、anthropic 和 litellm。心跳和定时任务可以单独指定模型。

官方公告还写：它出现在网页、终端、Slack 和 Microsoft Teams，并且“不会、将来也不会”接入 Telegram 或 WhatsApp 这类消费级聊天应用。这是公告里的产品定位。核验时在仓库内检索 Telegram 和 WhatsApp，没有得到命中，因此不宜把这句话理解成已经在源码里逐项核对过的接口清单。

到这里为止，文档证明的是：这个智能体可以被做成一个会自己醒来、能用工具、重启后还能接着跑的进程。接下来的问题才是，写在手册里的规则，能不能把它留下。

二、两道操作员控制，官方把它写成护栏，而不是安全边界

README 把面向公司的控制收成两件：工具风险门闩（tool risk gate）和锁定模式（locked-in mode）。它们确实存在，源码里也能看到对应实现，例如 src/lib/tool-risk-gate.ts。但配置文档对它们的定性，比功能列表更值得先读完。

工具风险门闩由 TOOL_RISK_GATE_MODE 打开，在工具真正执行前，用分类模型对照当前的「Agent Guide」做一次策略检查。它有三档：

  • off：不做评估。这是默认值，文档写明这样是为了保持原有行为和延迟。
  • observe：会评估并记录，但无论结论如何都执行；评估器失败时也是放行。
  • enforce：把判定为不安全的调用拦住；评估器出错或超时，这次被评估的调用也会被拦住，而不是放行。

也就是说，新装好的默认状态并没有打开这道门。文档建议先跑 observe，看清哪些规则会挡住工作，再考虑切到 enforce。策略来自你维护的 Agent Guide：你可以写得更严，也可以写得更宽；一条你写下的规则在它所覆盖的问题上优先于内置规则，因此也可以关掉对“大范围删除、暴露密钥、改权限”的拒绝。从未改过的指南不会被当成策略，新智能体只走内置规则；一旦你改了其中任何一段，整份文档（包括原来的例行句子）都会成为策略，所以文档提醒：如果「Safety」下还有“默认只读”这类句子，当作策略就会拒绝它完成工作所需的写文件和构建，需要先删掉再切换到 enforce。指南大约按 8,000 个字符读取，超长时取开头和结尾，中间的规则可能根本没被看到。

文档还写了两句不宜跳过的限定。第一，门闩检查的是启动编程任务的那次 coding_agent 调用；一旦放行，被启动的 Codex 任务“会在没有 Codex 沙箱的情况下运行，并能写到该用户能写到的任何地方”。第二，“这道门是纵深防御，不是沙箱”：主智能体和风险分类器都是语言模型，都可能判断错，“请把操作系统权限当作硬的安全边界”。src/lib/tool-risk-gate.ts 文件头也写了同一判断：这是纵深防御而不是沙箱，操作系统权限和沙箱网络策略仍是权威边界。

锁定模式针对的是另一件事：不让智能体改写自己。打开后，它自己的工具不能再改 Soul、User、Memory、Vision、心跳配置和 Bootstrap，也不能写入或删除长期记忆；智能体没有解锁自己的工具，只能由人在 Profile 页面或调用管理接口关掉。Agent Guide 本来就没有对应的写入工具，所以锁定并不额外保护它。

紧接着，配置文档用加粗写了一句：“锁是防止漂移的护栏，不是安全边界。”它列出了三个已知缺口：

  1. Shell 在任何模式下都不会被收走。 每个智能体都有 shell_exec。锁拿掉的是改文档的工具，不是命令执行。若命令跑在主机上，shell 可以直接改 /data/agent.db 里的文档，而且不会留下正常的修订记录，历史只会提示这份文档在应用外被改过。文档同时说：当命令在容器里运行时，数据库并不在智能体的那份可写存储里，这条特定路径是关掉的。docs/tools.md 也写了相应的执行位置：Docker 可用时，命令默认跑在容器里，碰不到智能体数据库；若设置 EXECUTION_ENVIRONMENT=local，或在某个仓库里直接启动 prism，命令会改跑在本机，那时工作区只是默认工作目录，不是边界，shell_exec 能运行该运行时操作系统用户被允许的任何命令。
  2. 容器内部看管理接口不需要凭据。 认证发生在容器前面，所以 shell 可以请求 PATCH localhost:3003/agents/locked-in 把锁关掉。“智能体不能自己解锁”说的是它的工具，不是这台机器上的 HTTP 接口。同一条 shell 还可以改 Soul 等文档，历史会记成你本人的编辑。
  3. POST /agents/import 不受这把锁限制。 它可以准备一整份替换用的数据库——文档、记忆、会话，以及锁本身的开关——运行时下次启动时换上去。

身份文档里对 Agent Guide 的说明是同一逻辑：没有写入工具，不等于没有改法；shell 永远在，容器内的管理接口也不要凭据，因此“这去掉的是模型做任务时会去找的那条普通路径，不是所有路径”。官方的收束句很清楚：锁住一个你希望它保持稳定的智能体；不要用锁去对付一个你并不信任的智能体。

三、能定时醒来，还差什么才谈得上“按规则留下”

下面这一节是本文的判断，不是项目文档里的原话。已核验的是规则当时怎么写；推论和尚未执行的设想会单独标明。

先说我认为它写清楚的地方。许多“自主智能体”只是把聊天窗口开着，或者用外部 cron 再调一次同一段提示词。Prism 把目标、日历、心跳、Webhook 和后台服务写进同一套运行时，并且把“没有新发现就不要吵”写成默认行为。就设计而言，这更接近“一个会按日程醒来的进程”，而不是“一次还没关的对话”。工具风险门闩和锁定模式也被明确写成可选的操作员控制，文档没有假装它们等于沙箱。把护栏和安全边界分开写，本身比只展示功能列表更有用。

接下来必须把两层主张拆开，否则很容易把“它能在你离开后继续跑”读成“你可以按手册里的规则把它留下”。

第一层只证明进程能醒、能用工具、能在重启后接着工作。心跳默认 8 小时一次、只在有新发现时发消息，说的是通知策略，不是权限策略。定时任务把送达目标设成 None，也只是“跑完不说话”，并不改变它当时能调用哪些工具。

第二层才是治理。门闩默认是关的；要把它当成拦阻，需要你显式切到 enforce，还先得读完整份会成为策略的指南。锁定模式能挡住普通的自我改写路径，但官方已经写出：命令执行不会被收走，容器内的管理接口可以关锁，导入接口可以连锁一起换掉。若命令跑在本机，直接改数据库这条路是敞开的；即便命令在容器里因而改不到数据库，后两个缺口也并不因此消失。把这些控制理解成“企业级无人值守已经就绪”，超过了文档自己愿意承诺的范围。官方写“enterprise-ready”“每个功能都经过端到端测试”“Mirantis 团队日常在用”，都是发布方的自我陈述。作者没有核对测试套件，也没有观察任何实际部署，不能把这些句子当成已经成立的效果。

一个可以直接验证、但本文尚未执行的做法是：先按官方文档完成一次安装，确认 TOOL_RISK_GATE_MODE 是否仍为 off，并查看当前执行环境是容器还是本机；再只打开 observe，用几条会改文件、会发消息、会调用编程子智能体的任务，看门闩记录了什么、有没有放行本该拦住的调用；确认锁打开之后，文档工具是否被拒绝，同时检查 localhost:3003 在容器内是否仍可被 shell 访问。在有自己的记录之前，不宜根据功能列表决定把凭证、生产集群或对外发送交给它无人值守。文档自己把硬边界放在操作系统权限上，这件事比星标或“面向企业”的措辞更稳定。

对想试用的人，我更看重这三条可操作的问题：定时任务和心跳唤醒时，用的是不是完整工具集，送达设置为安静是否被误当成已经降权；门闩是 off、observe 还是 enforce，Agent Guide 里有没有一条过宽的“允许”被整份文档一起生效；以及当前安装是本机执行还是容器执行，官方写出的三个锁定缺口，哪几条在你这台机器上仍然成立。项目刚公开不久，默认模型和接口都可能变化，这些问题反而比某一天的版本号更值得先问。

智能体“在对话结束后继续干活”，听起来像已经把人从回路里请了出去。Prism 的文档表明，它确实可以把醒来、做事和重启恢复做成同一套运行时；但它自己也写明，手册、门闩和锁定去掉的是常见改法，不是所有改法。先把“能定时醒来”和“能按规则留下”分开，再决定要不要让它在你不在场时继续调用工具。
