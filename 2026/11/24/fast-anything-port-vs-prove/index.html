资料核验：2026 年 11 月 24 日约 17:50—18:15（上海时间），依据 EL4CTEO/fast-anything 当时的 GitHub 元数据、LICENSE、README.md、Cargo.toml、v0.8.6 的 Release 说明、CHANGELOG.md、skills/fast-anything/SKILL.md，以及源码 src/main.rs、src/pipeline.rs、src/hotspot.rs、src/python/runner.py、src/native.rs，并对照当时的 npm 包页面 与 crates.io 页面。仓库、星标、版本和文档都会更新，计数与安装方式请以各官方页面与仓库文件的最新文本为准。本文只比较这些公开文本当时怎么写，作者没有安装、运行或测试该工具，也没有复现官方示例中的加速数字，不构成选型背书、效果承诺或性能结论。

编程助手已经很会写出一段能编译的 Rust。下一步常常是把整个程序交给它，等一份看起来更快的新代码。这时人很容易把两件事当成一件事：智能体写出了可替换的实现，以及这段替换在真实调用上仍然和原来一样。

这和本博客谈给编程智能体放权之前，先想清楚它在哪里必须停下有关，但本文不展开通用的权限分级，只看一套开源工具怎样把“改写范围”和“启用条件”拆开。它也和开源浏览器智能体，先分清谁在规划、谁在点击，以及成绩怎么测类似：找出该做什么、写出代码、以及用什么标准决定能不能换上，并不是同一层。

一、它要搬的是可移植的热点函数，不是整个程序

2026 年 11 月 24 日约 18:00，用 GitHub 接口读取 EL4CTEO/fast-anything 的元数据：公开仓库，主要语言 Rust，许可证 MIT，星标 3,378，fork 227。仓库创建于 2026 年 11 月 21 日 22:40（上海时间）；当时 main 上能读到的最新提交是 ccf46b49da（当天 08:18，上海时间），说明为暂存 npm 包。同一天 08:12 发布了正式版本 v0.8.6。项目主页指向 npm 包 @el4cteo/fast-anything；crates.io 当时列出的版本也是 0.8.6，许可证同样是 MIT。星标会继续变化，请以仓库页面当时的数字为准。

仓库很新，从创建到 0.8.6 只有大约两天半，版本号也跳得很快。讨论当前能力时，应以仓库文件、Release 说明和注册表页面的最新文本为准，不宜把某一天的示例数字当成稳定基准。

README 的标题句是：不要把整个程序改写成 Rust，只改那 5% 慢的部分。它把流程拆成几步，也可以一条命令跑完：

  • scan：给应用做性能分析，按“耗时占比 × 可移植性”给函数排序；
  • port：再跑一遍应用，最多记录 500 次真实调用，并生成一个只含这一函数的 Rust crate 和 TASK.md；
  • verify：用 release 模式构建移植结果，回放全部已记录调用；
  • enable / disable：用一段带标记的代码把 Rust 换进去或换回来，官方说明是可以按字节原样移除的；
  • bench：交错运行，比较整个应用在原实现和 Rust 之间的耗时。

--agent 可以是 claude、codex，或任何从标准输入读提示词的命令；不指定智能体时，把 TASK.md 交给自己使用的工具即可。官方还提供 Claude Code 插件、内置 MCP 服务器（README 写了 8 个工具）和一份 skill，用来把这套循环教给其他智能体。

语言支持以当时 README 表格为准：Python 3.10+（PyO3），JavaScript / TypeScript（Node 22+、Bun、Deno 2+，napi-rs），Ruby 3.3+（通过 Fiddle 调用 C ABI），Java 22+ 与 Kotlin/JVM（FFM），Go 1.22+，PHP 8.1+（需打开 FFI 扩展），C / C++，C# / .NET 8+，以及 R 4.0+。它要搬的，是接收普通数据（数字、字符串、列表、字典、定类型数组等）的顶层、确定性函数。scan 会写出其他函数暂时不能搬的原因。源码把“值得搬”写成同时满足三项：可移植、没有被外层可移植调用者覆盖、并且占这次运行至少 2%。

它还明确偏向搬最外层的热点循环，而不是循环里面那个小函数，这样应用进入 Rust 一次，而不是进出成千上万次。README 举的对照是：如果只移植内层的 levenshtein，官方表格里的加速会变成 35× 和 1.9×。这是项目自己的说明，不是本文的复现。

扫描阶段还有一条和验收直接有关的限制。源码把“做 I/O”“不确定”“写全局或静态状态”等写成会传递给调用者的阻断项，并注释说：verify 只比较返回结果，如果辅助函数做了这些事却被一起搬进去，一份跳过副作用的移植仍可能通过回放。2026 年 11 月 23 日的提交说明也写了：辅助函数做 I/O 的函数，本身也不可移植。

二、能不能启用，不由智能体宣布“写好了”来决定

这是这套工具更值得看的一层。智能体负责写 Rust；默认情况下，写完并不能直接换上。

verify 要先做 release 构建，再回放记录下来的真实调用。README 还写了：在这些调用之外，工具会派生额外用例，交给原实现作答，包括 NaN、正负无穷、-0.0、0 和 ±1、非 ASCII 文本、空输入、最多放大到 16 倍的输入，以及缩小后的输入。官方叙述里有一个示例：有一份“看起来是对的”移植按字节而不是按字符做比较，500 次真实调用里有 148 次抓住了它。这是项目自己的说明，作者没有复现这次失败。

Python 回放里的相等判断，比 README 那句“浮点在 1e-9 内视为相同”更细。src/python/runner.py 里的 same() 写明：浮点数用相对误差 1e-9、绝对误差 1e-12 比较，NaN 与 NaN 视为相同；但整数 3 和浮点数 3.0 不相等，因为打印结果不同；列表和元组也不相等，因为哈希行为不同。对走 C 桥接的语言，src/native.rs 里用的是：完全相等，或绝对误差不超过 max(1e-12, 1e-9 * max(|x|, |y|))。这些是当时源码里的比较规则，不代表所有语言、所有类型都按同一套实现。

enable 的默认门槛写在 src/pipeline.rs：还没通过 verify 不能启用；原文件在记录之后改过，或 Rust 源码在上次通过之后又改过，都要重新验证；如果每次调用反而比原实现更慢，默认也不会启用，并提示去移植它的调用者，减少跨越边界的次数。已经启用的移植如果后来没通过验证，会被自动换回原实现。环境变量 FAST_ANYTHING_DISABLE=1 可以在单次运行里强制走原实现。这些默认限制都可以用 enable --force 绕过——也就是说，机械门闩并不是不能打开，只是打开要人明确说。

三、回放契约证明了什么，以及它没证明什么

下面这一节是本文的判断，不是项目文档里的原话。已核验的是规则当时怎么写；推论和尚未执行的设想会单独标明。

先说我认为它做对的地方。许多“让智能体改写代码”的流程里，测试也是同一个智能体写的。测试和实现一起错，仍然可以显示全绿。fast-anything 把验收数据从另一条路上拿来：真实运行中的调用记录，再加上由原实现作答的边界用例，并在 skill 里写明不要改这些记录。启用权也不在对话里，而在回放是否全部通过、每次调用是否真的更快。就设计而言，这更接近“先有行为契约，再允许替换”，而不是“先相信模型已经写对了”。

接下来必须把契约的边界说清楚，否则很容易把“这次回放通过”读成“两个函数在所有输入上都等价”。

第一，记录来自你实际跑过的那次工作负载。官方 skill 也提醒：扫描要用有代表性的真实负载，而不是测试套件。没出现过的分支、很少走到的错误路径、更大或更畸形的输入，并不自动包含在这 500 次里。派生用例扩大了覆盖，但仍然是从已记录输入变出来的，不是对全部输入空间的证明。

第二，源码自己已经写了：验证比较的是返回值。被它拒绝搬运的 I/O、全局状态和不确定性，并不是因为这些东西不重要，而恰恰是因为现有回放看不见它们。如果扫描漏掉了这类副作用，一次“结果一致”的回放，证明不了文件、网络或共享状态也一致。

第三，官方性能数字全部来自 README 的示例表，标注运行在 i5-10500、Windows 11 上，C 和 C++ 则在 4 核的 GitHub Actions Linux runner 上，并说明可以从 examples/ 复现。表格里 Python 模糊去重（700 个名字）从 4.91 秒降到 42 毫秒（116×）；Java 的同类例子整应用只有 3×，函数本身 11×，其余是 JVM 启动。作者没有在自己的机器上跑这些例子，也没有核对表中数字。即使例子能复现，它证明的也是这类可隔离的纯函数热点，不能外推到任意业务程序。

一个可以直接验证、但本文尚未执行的做法是：先按官方步骤跑 examples/fuzzy-dedupe，只核对手册表格是否能得到同一量级的结果；再做一次只移植内层 levenshtein 的对照，看交叉调用成本是否明显吃掉加速；最后故意写一份按字节而不是按字符比较的错误移植，看 verify 会不会拒掉。在有自己的记录之前，不宜把手册表格当成已经到手的收益。

对想试用的人，我更看重这三条可操作的问题，而不是星标数字：这次扫描认为最值得搬的函数，是不是你自己也认为最慢的那段，阻断原因写得清不清楚；verify 用的记录，是不是来自你关心的那次负载，失败时能不能看到具体是哪一次调用不一致；以及启用之后，能不能用 disable 或 FAST_ANYTHING_DISABLE=1 立刻退回。项目还很新，接口和语言支持都可能在几天内变化，这些步骤反而比版本号更稳定。

用编程智能体去“改成 Rust”，容易变成一次范围不受限的重写。fast-anything 把范围收成可移植的热点函数，又把启用权交给带记录的回放。它能证明的，是这些记录和派生用例上结果一致，而且这次调用更快；它不能自动证明程序在所有输入上等价，也不能看见返回值之外的副作用。先把这两层分开，再决定要不要让智能体改下一处。
